# NetPulse — 14-Week Course-Aligned Plan

> Proposed plan only. Confirm exact dates with the KTU academic calendar and supervisor. The syllabus asks for two-week sprints; the course milestone weeks below are review anchors, not a reason to skip sprint reviews.

| Week | Course milestone | NetPulse work and evidence |
|---|---|---|
| 1 | Topic, synopsis, approval, Product Owner discussion | Stakeholder interview; problem validation; synopsis approval; initial product backlog; authorised target policy |
| 2 | Project commencement | Requirements baseline; use cases; architecture; initial ERD and wireframes; Sprint 1 plan |
| 3–4 | Sprint 1 release/review | Auth/roles, asset inventory, seed demo assets; unit/API tests; demo and dated review |
| 5–6 | Sprint 2 review; first board evaluation | Manual HTTP(S) and reachability probes; safe allow-list; timeout/error handling; history records; interim board evidence |
| 7–8 | Sprint 3 review | Scheduler with bounded intervals/concurrency; dashboard summaries; history filters and charts; regression tests |
| 9–10 | Sprint 4 review | Incident workflow, alert transitions, role checks, audit log; integration tests and demo |
| 11 | Second board evaluation | Stabilisation; security review; end-to-end demo; defect and risk status |
| 12 | Sprint 5 review | CSV report; accessibility; Docker/CI checks; backup and deployment notes |
| 13 | Report, Scrum Book, final presentation and board evaluation | Final report, evidence register, release candidate, demo rehearsal, unresolved limitations |
| 14 | External evaluation | Tagged build; final deployment verification; external examiner demonstration |

## Two-week sprint structure
- Sprint planning: set a measurable goal and choose backlog items.
- Progress meetings: less than 15 minutes, approximately once in three days.
- Sprint review: under 30 minutes; demonstrate working increment to Product Owner.
- Retrospective: identify one improvement and assign an owner.
- Scrum Book: maintain dated entries under Product Backlog, Database & UI Design, Testing & Validation, and Details of Versions.

## Suggested increments
1. Identity and asset inventory.
2. Safe manual probes and persisted check history.
3. Scheduled checks and health dashboard.
4. Incident workflow and alerts.
5. Reports, security hardening, deployment and final documentation.

## Required evidence to collect
- Stakeholder discussion notes with consent and dates.
- Approved synopsis and requirement changes.
- Use-case diagram, architecture, ERD, UI wireframes.
- Product backlog and dated sprint planning/review/retrospective notes.
- Screenshots of real running features, not mock screenshots presented as real.
- Automated test output and manual test records.
- Git commit history, tagged release, CI result.
- Docker start-up and API health-check evidence.
- Final report, presentation and deployment instructions.
