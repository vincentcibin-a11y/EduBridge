# Project Plan — EduBridge MCA Main Project

**Methodology:** Scrum | **Sprint duration:** Two weeks | **Course schedule:** 14 weeks

> This plan maps the course outline to EduBridge. Replace week markers with the actual KTU/FISAT calendar dates after confirmation. This is a plan, not proof that activities occurred. Record actual dates, attendees, approvals, feedback and evidence only after each event.

## 1. Project overview

EduBridge is a peer-to-peer academic doubt-solving and student tutoring platform for college communities. It supports doubt sharing, peer answers, tutor discovery, tutoring requests, notifications and post-session reviews.

## 9. Testing and validation strategy

- Unit / module testing for validation, authentication, authorization and business rules.
- API testing for endpoints, response codes and ownership restrictions.
- Integration testing across React, Express and MongoDB workflows.
- Regression testing after each sprint integration and defect fix.
- Manual browser acceptance tests with actual expected/actual results and screenshots.
- GitHub Actions CI for repeatable automated checks.
- Test Driven Development may be used for suitable modules; defects may be tracked in GitHub Issues, BugZilla, BackLog or an equivalent tool.

Never mark a test passed without executing it. Store the tested commit SHA and the actual command/log or screenshot.

## 11. Deployment pipeline

Current repository automation performs CI and Docker build validation; that is not the same as production deployment. Proposed deployment pipeline:

1. Developer pushes a Git commit to GitHub.
2. GitHub Actions installs dependencies and runs backend checks/tests.
3. CI validates Compose configuration and builds frontend/backend images.
4. An approved release is deployed to the selected hosting target.
5. Production MongoDB URI and JWT secret are supplied through protected environment settings.
6. HTTPS, allowed frontend origin/CORS, logs and backups are configured.
7. Health and smoke tests are run; deployment URL, release SHA and evidence are recorded.

Do not claim a production deployment until these steps have actually been completed.

## 13. Definition of Done

A backlog item is done only when acceptance criteria are met, code is integrated and committed, relevant tests are actually executed, failures are fixed or documented, evidence and documentation are updated, and a working increment is demonstrated at review. Record Product Owner feedback only when received.
